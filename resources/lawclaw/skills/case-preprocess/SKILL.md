# 案件材料预处理

> 三阶段管线：PDF → 可检索的结构化知识基座

## 触发条件

- 用户说"处理案件材料""预处理案件""整理XX案的PDF"
- 用户提供包含PDF的目录路径
- 用户上传案件PDF文件

## 输入

- `--input-dir`：PDF文件所在目录（必填）
- `--output-dir`：输出根目录（默认：Obsidian Vault 根目录）
- `--case-name`：案件名称（必填，用于子目录命名）

## 输出结构

```
{output-dir}/{case-name}/
├── 材料/                    # Stage 1: 提取的文本
│   ├── 起诉状.md
│   ├── 证据1-借款合同.md
│   └── ...
├── 提取报告.json            # Stage 1: 提取统计
├── 材料目录.md              # Stage 2: 材料索引+专家指引
└── 关系图谱.canvas          # Stage 3: 知识图谱
```

---

## Stage 1: 文本提取（Python脚本）

### 执行命令

脚本位于本 Skill 目录下的 `scripts/pdf_extract.py`。

- LawClaw Next：使用设置页检测到的本地 Python 执行 `<skill-dir>/scripts/pdf_extract.py`，不依赖 WSL

```text
<local-python> <skill-dir>/scripts/pdf_extract.py --input-dir "<用户提供的PDF目录>" --output-dir "<输出根目录>" --case-name "<案件名>"
```

### 脚本行为

1. 扫描目录下所有 `.pdf` 文件
2. 对每个PDF：
   - 先尝试 `pdftotext`（零成本）
   - 如果每页平均字符 < 50，判定为扫描型
   - 扫描型调用 PaddleOCR API 提取
3. 输出每个PDF对应的 `.md` 文件到 `材料/` 子目录
4. 生成 `提取报告.json` 记录统计信息

### 完成检查

- [ ] 提取报告.json 已生成
- [ ] 没有 "failed" 状态的文件（如有，向用户报告）
- [ ] 随机抽查1-2个MD文件，确认关键信息（金额、日期、当事人）完整

---

## Stage 2: 生成材料目录（Agent执行）

### 前置

读取 `提取报告.json` 确认所有文件已提取，然后读取 `材料/` 下每个MD文件。

### 生成流程

1. 逐个读取 `材料/` 下的MD文件
2. 识别每个文件的**文书类型**（起诉状/答辩状/判决书/合同/流水/聊天记录/证据/其他）
3. 提取每个文件的**核心信息摘要**
4. 读取 `references/expert-guide.md` 获取专家指引知识
5. 生成 `材料目录.md`

### 输出格式

```markdown
---
title: {案件名} - 材料目录
created: {今天日期}
case: {案件名}
---

# {案件名} 材料目录

## 一、材料位置索引

| 序号 | 文件名 | 文书类型 | 核心内容摘要 | 关键信息 |
|------|--------|---------|-------------|---------|
| 1 | 起诉状.md | 起诉状 | 原告张某诉被告李某... | 原告:张某, 被告:李某, 诉请:本金50万+利息 |
| 2 | ... | ... | ... | ... |

## 二、信息定位指引

> 需要什么信息 → 去什么文件找

| 我要找的信息 | 去哪个文件 | 具体位置 |
|-------------|-----------|---------|
| 诉讼请求 | [[起诉状]] | 第1段 |
| 借款金额 | [[借款合同]] | 第2条 |
| 转账记录 | [[银行流水]] | 全文 |
| ... | ... | ... |

## 三、案件概要

- **案由**：{自动识别}
- **当事人**：原告{姓名} vs 被告{姓名}
- **核心争议**：{一句话概括}
- **涉及金额**：{总金额}
- **关键时间节点**：{列出3-5个关键日期}
```

### 质量检查

- [ ] 每个文件都有类型识别和摘要
- [ ] 信息定位指引覆盖了案件的核心信息需求
- [ ] 案件概要的案由、当事人、金额准确

## Stage 3: 生成关系图谱（Agent执行）

### 前置

Stage 2 完成后，基于 `材料/` 下所有文件和 `材料目录.md` 提取实体和关系。

### 提取规则

从材料中提取以下六类实体：

| 实体类型 | 颜色代码 | 提取内容 |
|---------|---------|---------|
| 人物 | "4"（蓝色） | 姓名 + 角色（原告/被告/证人/代理人/法官） |
| 组织 | "5"（青色） | 公司/银行/法院名称 + 类型 |
| 金额 | "1"（红色） | 具体数字 + 上下文（本金/利息/赔偿） |
| 日期 | "6"（绿色） | 日期 + 事件描述 |
| 法律关系 | "2"（橙色） | 借贷/担保/买卖等 + 依据文件 |
| 证据 | "3"（紫色） | 证据编号+名称 + 证明目的 |

关系类型：借贷、担保、转账、代理、起诉、签约、催收、签署、证明、包含

### Canvas 生成规则

生成 Obsidian Canvas JSON 格式的 `.canvas` 文件。

**布局策略**：
- 人物节点放在左侧（x: -800 ~ -200）
- 法律关系节点放在中间（x: -100 ~ 400）
- 金额节点放在中上（x: -100 ~ 400, y偏上）
- 证据节点放在右侧（x: 500 ~ 1000）
- 日期节点放在关系节点下方（y偏下）
- 文件节点放在最下方（y: 600+），用 `type: "file"` 链接到 `材料/` 下的MD

**节点规格**：
- 人物节点：width 300, height 120
- 金额节点：width 280, height 100
- 日期节点：width 260, height 80
- 法律关系节点：width 280, height 120
- 证据节点：width 280, height 100
- 文件节点：width 300, height 100, type "file"

**节点内容**：
- 每个节点的 `text` 字段用 Markdown 格式
- 第一行是标题（`## 姓名/名称`）
- 后续行是关键属性（角色、金额、日期等）
- 标注来源文件（`来源: [[文件名]]`）

**边的规则**：
- 每条边必须有 `label`（关系描述）
- 使用 `fromSide` 和 `toSide` 控制方向（left/right/top/bottom）
- 同类型节点之间的边用两侧（left→right），跨类型用上下（top→bottom）

### 输出格式示例

```json
{
  "nodes": [
    {
      "id": "p1",
      "type": "text",
      "x": -600,
      "y": 0,
      "width": 300,
      "height": 120,
      "color": "4",
      "text": "## 张某\n**角色**: 原告\n**身份**: 出借人\n来源: [[起诉状]]"
    },
    {
      "id": "f1",
      "type": "file",
      "x": 500,
      "y": 600,
      "width": 300,
      "height": 100,
      "file": "{case-name}/材料/起诉状.md"
    }
  ],
  "edges": [
    {
      "id": "e1",
      "fromNode": "p1",
      "fromSide": "right",
      "toNode": "p2",
      "toSide": "left",
      "label": "借贷 50万元"
    }
  ]
}
```

### 质量检查

- [ ] 所有当事人都有对应的人物节点
- [ ] 每个金额都有上下文标注
- [ ] 关键法律关系（借贷/担保等）都有边连接
- [ ] 文件节点正确链接到 `材料/` 下的MD文件
- [ ] Canvas 在 Obsidian 中可正常打开（JSON格式正确）

---

## 全局规则

1. **顺序执行**：Stage 1 → 2 → 3，不可跳过或乱序
2. **Stage 1 失败处理**：OCR 失败的文件在 Stage 2/3 中标注"提取失败，需手动处理"，不阻塞后续
3. **禁止编造**：图谱中的实体和关系必须来自材料文本，不可推断不存在的关系
4. **增量处理**：如果 `材料/` 目录已存在且有部分文件，只处理新增的PDF
5. **文件命名**：提取的MD文件名与原PDF文件名保持一致（仅改扩展名）
6. **大文件处理**：单文件超过50页时，向用户确认是否需要OCR（耗时较长）

## 错误处理

| 错误 | 处理 |
|------|------|
| pdftotext 未安装 | `sudo apt install poppler-utils` |
| PaddleOCR API 超时 | 3次重试，仍失败则回退pdftotext结果并标记 |
| PaddleOCR Token 过期 | 告知用户需要更新 Token |
| 目录无PDF文件 | 报错退出，提示用户检查路径 |
| Canvas JSON 无效 | 检查节点ID唯一性和边引用完整性 |

## 快速命令示例

```
# 基本用法
预处理案件材料 "D:\案件\杨刚案" --case-name 杨刚案

# 指定输出目录
预处理案件材料 "D:\案件\张三借贷案\材料" --output-dir "D:\案件\张三借贷案\知识库" --case-name 张三借贷案

# 处理单个PDF
处理这个PDF /path/to/file.pdf --case-name 测试案
```
